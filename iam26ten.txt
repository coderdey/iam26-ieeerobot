How Does the Arm Know Where to Go? — The Full Chain

Right now test_ik.py just takes a hardcoded XYZ point. In the real pipeline, there are three coordinate systems that need connecting:

CAMERA FRAME                    ROBOT FRAME                  JOINT ANGLES
(ZED 2 sees pixels + depth)  → (meters from arm base)     → (degrees per servo)

     "object is at               "object is 12cm             "base=33°, shoulder=-15°,
      pixel (340, 280),           forward, 8cm right,          elbow=45°, wrist=-60°,
      0.35m deep"                 1cm above table              roll=0°"
                              from MY base"

   ZED SDK gives this         QR calibration gives          IK (from URDF) gives
   automatically               the transform                 this automatically

Step 1 — Camera finds object: ZED SDK gives you pixel coordinates AND 3D position in the camera's own frame (XYZ in meters relative to the camera lens).

Step 2 — Transform to robot frame: The QR calibration computes a 4x4 matrix that converts camera coordinates to coordinates relative to the arm's base. This is why you need the QR codes — they tell the system "the camera is HERE relative to the arm."

Step 3 — IK computes joint angles: Given "I need the gripper at [0.12, 0.08, 0.01] meters from my base," the URDF-based IK calculates what angle each of the 5 joints needs to be.

For TWO arms: Each arm has its own base position and its own QR calibration transform. The camera sees everything, but the transform converts to "meters from LEFT arm base" or "meters from RIGHT arm base" depending on which arm you're commanding.

# Simplified version of what happens at runtime:

# Step 1: Camera
bgr, point_cloud = zed.grab()
pixel_x, pixel_y = yolo_detect(bgr)  # or HSV detect
cam_xyz = zed.get_3d_point(pixel_x, pixel_y, point_cloud)  # e.g. [0.3, -0.1, 0.5]

# Step 2: Transform to robot frame (different per arm)
robot_xyz_left  = T_cam_to_left_arm  @ [cam_xyz, 1]  # e.g. [0.12, 0.08, 0.01]
robot_xyz_right = T_cam_to_right_arm @ [cam_xyz, 1]  # e.g. [-0.15, 0.08, 0.01]

# Step 3: IK
joint_angles = chain.inverse_kinematics(robot_xyz_left[:3])
# --> [base=33°, shoulder=-15°, elbow=45°, wrist=-60°, roll=0°]

Today's test_ik.py uses hardcoded points — that's fine for testing whether IK + URDF gives correct joint angles. The camera + transform chain comes later.

# scripts/test_ik.py — updated for SO-101
import ikpy.chain
import numpy as np

# Use the SO-101 URDF your teammates got working
chain = ikpy.chain.Chain.from_urdf_file(
    "../urdf/so101.urdf",
    active_links_mask=[False, True, True, True, True, True, False]
)

# Test: move to a point 10cm forward, 10cm up from base
target = [0.10, 0.0, 0.10]
angles = chain.inverse_kinematics(target)

# Verify: does FK reach the same point?
fk = chain.forward_kinematics(angles)
reached = fk[:3, 3]
error_mm = np.linalg.norm(reached - target) * 1000
print(f"Target: {target} | Reached: {np.round(reached, 3)} | Error: {error_mm:.1f}mm")

# If error < 10mm, IK is working. Then test on the real arm.

If this gives < 10mm error in simulation, then send the angles to the real arm and see if it goes to the right spot. If not, the URDF doesn't match the physical arm.

# Quick test: IK angles → real servo positions
from scservo_sdk import PortHandler, PacketHandler
import numpy as np

PORT = "/dev/ttyACM1"
SERVO_CENTER = 2048
COUNTS_PER_DEG = 4096 / 360.0

ph = PortHandler(PORT)
ph.openPort()
ph.setBaudRate(1_000_000)
pk = PacketHandler(0)

# angles_deg from IK (replace with actual values from test_ik.py)
angles_deg = [33.2, -15.1, 45.3, -60.2, 0.0]

for servo_id, angle in enumerate(angles_deg, start=1):
    pos = int(SERVO_CENTER + angle * COUNTS_PER_DEG)
    pos = max(0, min(4095, pos))
    pk.write2ByteTxRx(ph, servo_id, 46, 200)  # slow speed

YOLO Photos

All objects together, varied arrangements. Not one color at a time. Here's why:

- YOLO needs to learn to distinguish objects when they're next to each other
- Competition has all colors + shapes on the table simultaneously
- Vary: positions, spacing, which objects are near which, lighting

What to capture:
- 200+ photos total
- Mix of all objects on the table together
- Some photos with objects close together / touching
- Some with objects spread out
- Different lighting if possible (overhead light on/off)
- Different bin positions
- Include empty workspace photos (helps with false positive reduction)

Three modes:
- python pybullet_pick_place.py — sim only, watch the full pick-and-place sequence
- python pybullet_pick_place.py --real — sim runs first, then same angles sent to physical arm
- python pybullet_pick_place.py -i — type any XYZ, watch arm move (add --real to move physical arm too)

The interactive mode (-i) is your best friend today — type coordinates, see if the sim arm goes there correctly, and if --real is on, the physical arm follows. You can also type home, open, close for gripper control.
